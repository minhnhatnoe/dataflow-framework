## The model

### Node kinds
All subscribable things are nodes: one sealed `Node` trait with `type Output` and `type Init<'a>`.

1. **Root.** Exactly one per pipeline: `#[derive(Root)]` on a user type such as `struct Poll;` or `enum Wake { Nic0, Nic1 }`.
   - Fed by `pipeline.push(value: R)`. One push is one step.
   - No state, no subscriptions, nothing stored. Its value exists only during the push.
   - `Init<'a> = ()`.
2. **Demuxers.** Stateless pattern tests on a parent node's output (the root or any component). The output is a reference to the matched part.
   - `#[derive(Demux)]` on an enum generates a module named after the enum in snake_case, with one generic demuxer type per variant, `mod packet { pub struct Binance<P>(..); … }`. `packet::Binance<P>` requires `P: Node<Output = Packet>` and has `Output = BinanceMsg` (the variant's single field; support tuple variants with exactly one field, plus unit variants with `Output = ()`).
   - `Option`'s `Some<P>` / `None<P>` are built in.
   - A hand-written `Demux` trait covers guards: `type Parent: Node; type Output; fn demux(x: &<Parent as Node>::Output) -> Option<&Self::Output>;` (or a version returning a reference into the parent value).
   - No state, nothing stored, `Init<'a> = ()`.
   - Demuxers are the only run-time branches.
3. **Components.** Ordinary, user-written.
   - `#[derive(ComponentSubscription)]` + `#[subscribe(name: NodeType, ...)]`, as today (aliases and position tags `Sub<T, I>` still apply).
   - `impl Component`:
     ```rust
     type Config: Default + 'static;
     type Output: 'static;
     fn new(config: Self::Config, init: Self::Init<'_>) -> (Self, Self::Output);
     fn update(&mut self, input: Self::Input<'_>) -> Self::Output;
     ```
   - The derive generates both structs:
     - `Input<'a>`: one `&'a <T as Node>::Output` per subscription;
     - `Init<'a>`: one `<T as Node>::Init<'a>` per subscription, which is `&'a Output` for components and `()` for the root and demuxers.
   - A component's latest output is **stored** in the pipeline and persists between pushes. It always fires when it runs.
   - A sink is just a component (typically `Output = ()`).
   - The framework never invents an `Option` for user-visible inputs.

### Rules for one step (`push(r)`)
1. **Cone.** Only nodes downstream of the root can run. With a single root that is everything, but rule 2 still prunes.
2. **OR.** A component runs in this step iff at least one of its upstream nodes **fired** in this step.
   - The root fires on every push.
   - A component fires iff it ran.
   - A demuxer fires iff its parent fired and the pattern matches.
   - Upstreams that did not fire supply their stored output (components only; see rule 5).
3. **Once and in order.** Each component runs at most once per step, in depth-first post-order following subscription listing order: the existing guarantee, restricted to what runs.
4. **Joins (compile time).** Each node's condition, a set of terms, is computed in the plan.
   - A term is the list of demuxer decisions (demuxer node plus variant) on a path from the root.
   - A component's condition is the union of its upstreams' terms.
   - **Absorb:** drop any term implied by another (B's decisions a subset of A's means A implies B, so drop A). A term with no decisions ("always") absorbs everything.
   - **After absorption the remaining terms must be pairwise mutually exclusive:** two terms are exclusive iff they pick *different variants at the same demuxed parent*. Otherwise it is a compile error (const panic) with the message `"<component> joins branches that can fire in the same step"`.
   - A guard demuxer (hand-written `Demux`) has one variant only, so two guard terms are never exclusive, and a guard is never exclusive with anything except via another decision on the same path.
5. **Demuxer readers (compile time).** A component may subscribe to a demuxer, or directly to the root, only if its own condition implies that node fired (each of its terms implies the node's condition). Otherwise it is a compile error: `"<component> reads <demuxer> in steps where it does not fire; subscribe to a component that stores it"`.
6. **Unreachable (compile time).** A component reached by no path from the root is a compile error: `"<component> is not reachable from the root"`. So is a graph whose root type differs from `R`, or that contains a second `#[derive(Root)]` type.

### Implementation guidance (choose the details; document them)
- **Plan.** The plan records each node's kind (root, demuxer + variant id + parent, component) and, per component, the list of its upstream node indices. It computes conditions and runs the checks of rules 4–6 in const eval, as integer arrays (invariant 2). It must stay bounded and cheap (`MAX_COMPONENTS` 512; terms per node are bounded by the number of exclusive branches; pick a sane constant cap and panic clearly past it).
- **Storage.**
  - **States:** a balanced flat tuple of component states by execution position, with `()` at root/demuxer positions or with those positions excluded.
  - **Outputs:** a separate balanced flat tuple of stored outputs.
  - Construction runs in execution order. Each `new` receives `Init` built from the already-constructed outputs (use the flat experiment's construction / finished-left-siblings context mechanism, since outputs are built incrementally there).
- **Push.**
  - Suggested safe scheme:
    - Keep a per-step `[bool; N]` "fired" array indexed by const positions (LLVM turns it into scalars).
    - For each component position in execution order: `if <its condition: OR over the fired flags of its upstreams> { let out = state.update(inputs from &outputs + &root, demuxers re-matched from their parent's value); outputs[P] = out; fired[P] = true; }`.
    - Demuxer fired flag = parent fired && pattern matches on the parent's current value (the root value or the parent's stored output).
    - Components whose absorbed condition is "always" get no check.
  - Borrow order: inputs borrow `&outputs`/`&root` only while computing the update; the write to `outputs[P]` happens after the update returns. **No `unsafe`.**
  - The hand-written equivalent is a nested `match`. Measure whether LLVM produces comparable code (see the benchmark).
- **Identity, configs, cycle detection, aliases/`Sub<T, I>`, `MAX_COMPONENTS`:** keep as on master.
- **Generic user code:** exactly one bound in user code for "this is a valid pipeline" (e.g. `R: Root, S: Sinks<R>` or a single `Valid` bound); document it; keep the `generic_user` test idea.
- **Feature gates:** user crates need no `#![feature]`.

## Caching and merging per-component resolution (user, 2026-11-01)

Most components will live in a **shared, relatively stable library crate**; the app wires them together. Find ways to resolve each component once, cache that, and merge cheaply. Hypotheses, in order of cost; measure each at the typical size and at 29,650 components:

1. **Make all root-independent work local to the component.** This means the derive's `Input`/`Init` structs, the subscription list, `TypeId`/name hash, and demuxer metadata. It should be non-generic consts and types emitted in the component's own crate, so it is compiled and cached there. Today almost everything is parameterised by the root `R` (`At<R, C>`, positions), so nothing is reused. Move as much as possible out of `R`-dependent items, so the app crate only does the *merge*: positions, conditions and cones over small integer summaries.
2. **Keep structure and behaviour separate.**
   - Editing a component's `update` *body* must not change any type or const the plan depends on. Then incremental compilation reuses the whole type-level resolution, and only that function (plus push in release) is rebuilt.
   - Verify with `-Zincremental-info` / self-profile that a body edit in the big component re-runs no plan or trait queries.
   - Keep components in separate modules/files: span changes are per file.
3. **Non-generic cores.**
   - Generic families such as `Book<D>` × 2,214 should have a tiny generic wrapper that calls a non-generic core (`BookCore::apply`) compiled once in the library crate.
   - Document this as the recommended pattern; the bench generator should use it for its library-style components.
   - Check what `-Zshare-generics` and cross-crate inlining do: release needs inlining; dev should not inline across crates.
4. **Dev-build settings.** No forced inlining in debug; more codegen units; maybe `-Zshare-generics=y`. Measure the incremental rebuild after editing the big component plus a few small ones.
5. **Fragments (if 1–4 are not enough at 30k).** Allow a library to define a pre-resolved subgraph, e.g. one market's ~10 components below its demuxer. Its positions, storage tuple, conditions and lookups are resolved *relative to the fragment*, inside the library crate. The app's plan treats each fragment instance as one node with an offset.
   - A fragment exposes its outputs and may take imports (components outside it) as parameters.
   - The merge is then O(fragments), not O(components).
   - Prototype it, measure, and report the trade-offs (singletons across fragments, joins, order guarantee).

## Merged listeners: one websocket for many symbols (user, 2026-11-01). Build in phase 2.

**Problem.** `Book<S>` needs a feed for symbol `S`. One websocket per symbol is expensive. We want one listener per exchange (or per connection shard) that subscribes to *exactly the symbols the graph uses*, and demuxes its messages by symbol.

**Solution: keyed demuxers, plus requests that flow upstream.**

1. **Symbols carry an integer key.**
   - `trait Symbol: 'static { const KEY: u32; const NAME: &'static str; }`. In the library's market catalog these are dense per exchange: 0..n, generated from the exchange's market list.
   - Different stream kinds can be part of the key (`depth`/`trades` × symbol), or a separate demux level.
2. **The keyed demuxer `On<S, P>`** (built in). `P`'s output must implement `Keyed { fn key(&self) -> Option<u32>; type Item; fn item(&self) -> &Self::Item; }`.
   - `On<S, P>` fires iff the parent fired and `key == S::KEY`; its output is `&Item`.
   - **Exclusivity:** two keyed demuxers on the same parent with different keys are exclusive (the plan's decision = (parent, key)). Enum variants are the same idea, with the key = the variant index.
   - The same key through different alias types is the same decision.
3. **Requests flow upstream at build time.**
   - The plan records, for each component, the keys of the keyed demuxers that have it as their parent (deduplicated, integer arrays).
   - A component opts in with a trait such as `Listener { fn subscribe(&mut self, keys: &[u32]); }`, declared through the derive (e.g. `#[listener]`) so the plan knows statically.
   - `Pipeline::build` calls `subscribe` once, after construction and before the first push, with exactly the requested keys.
   - The listener maps keys to stream names through its catalog and opens one connection with a combined subscription. If the exchange caps streams per connection (Binance documents a per-connection limit for combined streams), it shards internally over several sockets but stays one component.
   - Symbols nobody reads are never subscribed.
4. **Usage.**
   ```rust
   type Depth<S> = payload::Depth<On<S, Some<BinanceWs>>>;   // payload kind is an ordinary enum demux

   #[subscribe(upd: Depth<S>)]
   struct Book<S: Symbol>(..);
   ```
   `Book<Btc>` and `Vwap<Btc>` share the node `On<Btc, Some<BinanceWs>>`, so BTC is requested once.
5. **Dispatch at run time must not be linear in the number of symbols.**
   - With 2,214 keyed siblings, testing each guard in turn is unacceptable.
   - Group the keyed siblings of one parent into a decision tree over their sorted const keys, so that LLVM can lower it to a `switch` / jump table: `key < MID ? left : right`, built type-level from the plan's sorted key list.
   - Each leaf runs that key's cone straight-line (components joined across keys, such as a sink, are copied into each leaf; this is the exclusive-join rule).
   - This "one straight-line leaf per exclusive term" codegen is also the run-time-optimal form for enum demuxers. Phase 4 should move push codegen to it if the flag-based form from phase 1b does not reach parity.
6. **Checks.**
   - Keyed demux on a parent whose output isn't `Keyed`: compile error.
   - Duplicate key with conflicting types: compile error.
   - `subscribe` is always called before the first push (test it).
   - The exchanges example and the market-sized bench use this.

## Demuxing on the subscription edge, not as nodes (user, 2026-11-01). SUPERSEDES "Demuxers" as user-facing nodes

The user wants no demux *nodes* in the graph: each component's subscriptions carry their own demuxing. The graph's user-visible nodes are only **the root and components**.

**Syntax.** A subscription can have a chain of *selectors* applied to the parent's output:
```rust
#[subscribe(upd: BinanceWs => Some, payload::Depth, On<Btc>)]   // parent, then selectors applied left to right
#[subscribe(w: Wake => wake::Nic1)]                             // demux the root
#[subscribe(book: BtcBook)]                                     // plain, as before
```

**Selectors** are zero-sized types, *not* nodes:
```rust
trait Select<In> { type Out; const KEY: u32; fn select(x: &In) -> Option<&Self::Out>; }
```
- `#[derive(Demux)]` on an enum generates one selector per variant in a snake_case module (`payload::Depth`), with no parent parameter. `KEY` is the variant index.
- `Some`/`None` are built in. `On<S: Symbol>` is the keyed selector (`KEY = S::KEY`, via `Keyed`).
- A guard is a hand-written `Select` impl.
- The field type is the chain's final `Out`, named by projection, e.g. `&'a <Chain as SelectChain<<P as Node>::Output>>::Out`. So the derive needs no type inference. The `Init` field for a selected edge is `()`.

**Semantics.** These are the same rules as before, but stated per edge:
- **Firing.** An edge fires iff its parent fired *and* every selector matched. A component runs iff any of its edges fired (OR).
- **Conditions.** A term is a list of decisions `(parent node, selector position, key)`. Absorption works as before, and exclusivity holds for two decisions at the same parent and position with different keys.
- **Rule 5 per edge.** A selected edge's value exists only while its selectors match the parent's *current* value. So a component's condition must imply each of its selected edges, or it is a compile error ("subscribe to a component that stores it"). Plain edges read stored outputs as before.

**Internals.** The plan builds, per parent, a *decision trie* from all outgoing edges' selector chains. Shared prefixes, e.g. `Some, payload::Depth` used by many components, are matched once per step. Push codegen dispatches through the trie (enum keys and sorted keyed siblings become `switch`-able decision trees); its leaves run cones straight-line. Internally these trie nodes may be represented like the phase-1b demuxer nodes (positionless, stateless), but they never appear in user types.

**Merged listeners** (previous section) use the same trie: the keys at a parent's `On<_>` positions are its requests, passed to `Listener::subscribe(&keys)` at build.

Benefits: no generated parent-parameterised node types; short subscriptions; one node kind besides the root; the phase-1a position problem for demux nodes disappears.

## Handler components: a second way to define a component (user, 2026-11-01). Build after phase 1b; it coexists with `Component`

**Use case.** An OMS subscribes to many quoters, and only the quoters that updated in this step matter.

**API sketch.**
```rust
#[derive(Handler)]
#[handles(Quoter<Btc>, Quoter<Eth>, Quoter<Sol>)]   // or a type list from the catalog, e.g. `Quoter<S> for S in AllSymbols`
#[subscribe(limits: RiskLimits)]                      // optional plain subscriptions, read in `finish`
struct Oms { scratch: Vec<Order>, .. }

impl Collect for Oms {
    type Config; type Output; type Buf;
    fn new(config: Self::Config) -> Self;
    fn begin(&mut self) -> Self::Buf;                 // e.g. std::mem::take(&mut self.scratch): no allocation
    fn finish(&mut self, buf: Self::Buf, input: Self::Input<'_>) -> Self::Output;  // input: plain subscriptions
}
impl<S: Symbol> UpdateHandler<Quoter<S>> for Oms {
    fn on_update(&mut self, buf: &mut Self::Buf, q: &QuoteDecision) { buf.push(q.order()) }
}
```

**Semantics.**
- A handler component is a node like any other (`Node`, a stored `Output`), and runs iff any handled edge or plain subscription fired (the OR rule).
- When it runs:
  1. `buf = begin()`;
  2. `on_update(&mut buf, value)` for **each handled edge that fired in this step**, in execution order;
  3. `output = finish(buf, plain inputs)`, which is stored.
- **Edges that didn't fire are never read.** So rule 5 (selected-edge values must be implied by the condition) does **not** apply to handled edges, because a handler is only called when its edge fired. Rule 4 (exclusive joins after absorption) still applies, as a cost rule.
- **Inside each exclusive leaf/arm**, the set of fired handled edges is known statically, so the push is a straight line: `begin`, one `on_update` per fired edge, `finish`. No flags, no loop over quoters, the same cost as hand-written.
- **Initial output.** At build, the framework calls `begin`, then `on_update` for every handled edge with its initial value (those that have one: components; selected edges have none), then `finish`, as if everything fired once. Hence `new(config) -> Self`, with no `Init` struct.
- **Handled edges** can be plain or selected (`#[handles(f: OrderWs => Some, fills::Fill)]`).
  - The handler impl is keyed by the edge's node type: the parent type for a plain edge, or a derive-generated marker per named selected edge.
  - Generic impls (`impl<S> UpdateHandler<Quoter<S>>`) cover families. The list of instances must be given explicitly (Rust can't enumerate impls): either as a tuple, or as a catalog type list such as `AllSymbols`. This partly realises the stashed "subscribe to a set of instances".
- **It coexists with `Component`.** Both derive into the same `Node`/plan machinery, and a node can subscribe to either.

**Tests.**
- Only fired quoters reach `on_update`, in order.
- `finish` runs once per step.
- The initial output is built through the handlers.
- Plain inputs work in `finish`.
- Lifecycle and the exclusive-join error still hold.
- Profile it: run time in the exchanges bench against a hand-written OMS, plus compile time.
